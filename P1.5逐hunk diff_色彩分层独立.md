## 第一部分：需求描述——「色彩标签各管各的」

### 1.1 用户提出的目标形态

最终用户是非程序员的爵士萨克斯手。当前 P1 的色彩模型是：三张设置卡（Guide/Basic/Master/Learning）里的 Conserv/Ext 宽度胶囊**全部绑同一个全局键 `colorModeRaw`**，改一处三处联动；Guide 卡的宽度胶囊同时管「骨架线条色彩（guideLineColorEnabled）」和「Transform 加花 ✝（guideColorEnabled）」两件事。这对用户造成困惑：一个控件管了信号链上不同位置的两件事。

用户要求改为**信号流式、各管各的**：

1. **设置卡片只管本链路「裸生成」的色彩**：
   - Guide 卡的 Allow Color Tones + 宽度，只管生成的 Guide tone line（骨架）里有没有色彩音、色彩音多宽；
   - Grammar（Basic/Master）卡的 Allow Color Tones + 宽度，只管基于语法直接生成的 solo 里有没有色彩音、多宽；
   - Learning 卡同理，只管神经网络直接生成的旋律。
2. **调音台只管 Transform 加花后最终输出的色彩**：
   - 点亮 TRANSFORM 再点亮 ✝ 后，调音台内出现 Conserv/Ext 胶囊，控制「Guide+Transform」或「Grammar+Transform」最终 solo 里色彩音的宽度；
   - ✝ 不亮，加花输出不保留色彩音。
3. Learning 下 TRANSFORM 本来就置灰（引擎不作用），维持现状。

## 第二部分：Java 原版设计调研（说明本需求为何不偏离原版）

### 2.1 Java 本身就有「两道色彩闸门」

**闸门①——源头生成时要不要色彩：**

- Guide：`GuideToneLineDialog` 有一个 **Allow Color Tones 勾选框**，只在生成线条时传给 `GuideLineGenerator`：
  - `imp/guidetone/GuideToneLineDialog.java:679`：`boolean allowColor = allowColorBox.isSelected();`
  - `:686-695`：`new GuideLineGenerator(..., allowColor)` → `makeGuideLine()`。
- Grammar：色彩是语法内置概率参数（`color-tone-weight`，见 `grammars/chord.grammar:5` = 0.15），语法展开时本就概率性产生色彩音，源头没有用户开关。

**闸门②——整流（Rectify）是最终裁决权：**

- 全局三个勾选框 chord / color / approach，**出厂状态 = true / false / true**：
  - `imp/lickgen/LickgenFrame.java:1253`：`chordBox.setSelected(true);`
  - `:1276`：`approachBox.setSelected(true);`
  - colorBox 无 setSelected 调用 → JCheckBox 默认 **false**。
- Grammar 生成完默认整流：`rectifyCheckBox.setSelected(true)`（LickgenFrame.java:1235），putLick 时执行（Notate.java:13754-13755）。
- Transform 加花完也默认整流：TransformPanel 的 `substitutorRectifyCheckBox.setSelected(true)`（`imp/transform/TransformPanel.java:421`），加花后 `:1594-1597` 调 `notate.rectifySelection(...)`。
- 整流选项统一来自 LickgenFrame 的三个框：`LickgenFrame.getRectifyOptions()`（:7082-7089）→ chord/color/approach。
- **结论：Java 里 Guide+Transform、Grammar+Transform 两条链路，加花后由同一个 color 框做最终裁决**——color 不勾，最终只留和弦音+趋近音（加花产生的色彩音被拔，Guide 骨架原有的色彩同样被拔）；勾上，才允许色彩音留下。

**Transform 引擎自身没有「宽度」概念：**

- `imp/lickgen/transformations/Transform.java:213`：`applySubstitutionsToMelodyPart(melody, chords, enforceDuration)`——第三个布尔是**时值守恒**（Enforce Duration Equality），不是色彩。
- 加花只负责替换/加音，留什么全靠整流。
- 短促趋近音在整流中豁免（半音趋近且马上解决的音保留），Swift 对应 `GrammarLickGlue.swift:525-541`，任何宽度下都保留。

### 2.2 Java 没有 conservative/extended 宽度；色彩集合是和弦符号自带的

- 全 Java 源码搜索 "conservative" 仅出现在：① Help 文本里描述 LSTM **Risk Level** 的保守端（`imp/gui/HelpDialog.java`）；② LSTM 面板标签（`imp/lstm/main/LSTMNetworkFrame.java`）。**与色彩宽度无关**。
- 每个和弦符号的色彩集合写死在词汇表 `vocab/My.voc` 的 `(color ...)` 字段，例：

| 和弦 | My.voc 位置 | color 内容（相对 C 根） |
|---|---|---|
| C7 | :2358 | a（13） f#（#11） db（b9） d（9） d#（#9） g#（b13） f（11）——全量 |
| C9 | :2676 | a（13） f#（#11） g#（b13） f（11） |
| C13 | :2840 | db（b9） eb（#9） f#（#11） |

（9 在 C9/C13 的 spell 里；C13 的 spell 含 a=13。）

### 2.3 Swift 侧对应关系与等价口径

- Swift 的 `ColorPaletteMode.full`（UI 显示 Extended）= Java 词汇表全量色彩，P1 探针已验证 **full 与 Java colorBox 勾选逐音对齐**。
- Swift 的 `ColorPaletteMode.conservative`（只留自然 9/11/13，滤 b9/#9/b13/#11）是 Swift 已批准的**增强档**，Java 无此态；它不破坏对齐（full 能力保留）。
- 用户的「卡片管源头 / 调音台管 Transform 最终整流」恰好对应 Java 的闸门①/闸门②，只是把 Java 的全局 colorBox 搬到了更直观的位置。
- Learning 不经过 Transform：`BandMixerView.swift:96` `transformInteractive = !isLearning`，与 Java 相同（Java 的 Transform 作用于语法/线条产物，LSTM 面板独立）。

### 2.4 有意变更（已知晓，需用户确认）

1. **Grammar+Transform 的最终色彩闸门改为 ✝**：P1 时 ✝ 在 Grammar 组不显示，若 Grammar 卡色彩开 + Transform 开，最终保留色彩；新行为下必须 ✝ 开才保留（对齐 Java 全局 colorBox 的最终裁决）。**出厂默认（色彩全关）输出不变。**
2. 全局 `colorModeRaw` 拆为四个宽度键；默认全 conservative，**默认输出与 P1 逐音相同**。
3. 屏幕音符染色跟随「最终实际听到的输出」的宽度（见 D7）。

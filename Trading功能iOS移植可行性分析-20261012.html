Impro-Visor「Trading」功能 iOS 移植可行性分析

分析对象：教学视频 youtu.be/Xfk8vR2vsb4（作者 Bob Keller 演示）· 源码 /Users/onlyonear/Desktop/Impro-Visor-master · 目标：你的 iOS 应用 RealimPro（MIDI 键盘接 iPad，实时“互相用音乐对话”）
本报告仅做分析，未改动任何软件代码。

可行实时输入 + 音乐对话

iPad 用 CoreMIDI 接 MIDI 键盘、用 AVAudioEngine 发声，平台能力完全够，且芯片算力比演示用的桌面机更强。学术界已有同类 iOS 应用（GimmeDaBlues）佐证。

不能 1:1“完美移植”

不存在可直接搬的移动版，社区也无人做过。Trading 强依赖 Java 桌面特有的 javax.sound Sequencer（播放时钟），这部分必须在 iOS 上重新设计，而非翻译。

已过半你的基础已具备很多

RealimPro 已手工移植 Transform、Grammar、伴奏型 StyleEngine、LSTM、rectify、倒影/逆行 等全部“生成算法”。真正缺的是实时 MIDI 输入与轮流调度状态机。

一句话结论：“对话”效果可以在 iPad 上实现，而且能做得很好；但它不是把代码原样搬过去，而是用你已有的生成引擎 + 新建一套实时输入与轮流调度来“复刻”这套交互。

一、视频里到底演示了什么

硬件与场景

  • 笔记本运行 Impro-Visor，外接 Casio PX-5S 主控键盘（通过 USB/音频接口），监听音箱。
  • 示例曲目 Autumn Leaves（G 小调），软件根据和弦自动生成贝斯 / 鼓 / 钢琴伴奏。
  • 先区分两种输入：步进输入（Step entry）逐个填音符；实时输入（Real-time）边弹边录。

Trading 的交互方式

  • 对话框里选：谁先开始（人 / 电脑）、是否数拍、每轮长度（默认 4 小节，即 trading fours）。
  • 启动后进入“轮流”：人弹 4 小节 → 电脑回 4 小节 → 循环，像爵士乐手在台上“互相甩乐句”。
  • 结尾用 Pitch Tracker：拿口风琴（原声乐器）吹，软件把音频实时识别成 MIDI，再参与对话——这是“音频输入”扩展，与 MIDI 键盘路径不同。

视频展示的 7 种“回应”模式

  1. Repeat 重复：原样把你弹的回敬给你。
  2. Repeat & Rectify 重复并修正：节奏照抄，把音高“掰”到当前和弦的正确音上。
  3. Modify & Rectify 变形并修正：把你的乐句做倒影 / 逆行后再修正。
  4. Abstract Melody 抽象旋律：提取旋律轮廓，在不同音高重新“具象化”。
  5. Transformation 风格变换：用某位大师（如 Charlie Parker）的规则改写你的乐句——最核心的“音乐对话”。
  6. Grammar 语法生成：用生成语法独立造一句回应。
  7. Chop & Memorize 切碎记忆：把你弹的片段切分、记忆，再重组回放。

视频要点：决定“对话感”的不是发声，而是轮流时机的精确性与回应算法。

二、Trading 的源码架构与数据流

纯算法逻辑（易移植 / 你已移植） javax.sound 桌面特有（需在 iOS 重写） 调度 / 待补组件

关键观察：① 整套系统以 Sequencer 为绝对主时钟——录音、轮流、发声都靠它对齐；② 回应生成是“边界处才跑”的纯算法（默认 1 拍的处理窗口内完成，规则引擎只要几毫秒）；③ 桌面端甚至为每次回应新建一个 Sequencer，靠 slot 对齐。这在 iOS 上要换成“单一时钟 + 统一调度”。

五、你已具备 vs 需要新建（差距清单）

已经具备（140 个 Swift 文件）

  • TransformEngine：Transform / Substitution / Transformation / Evaluate / NCP / Scorer / 学习器 / 音乐家注册表。
  • Grammar：Grammar / 终端 / 概率表 / 各种 rectify。
  • MidiPlayer + StyleEngine：伴奏生成、贝斯/鼓/和弦 pattern 渲染、swing 弯曲。
  • AVAudioEngine + 4 个采样器 + 混响，SoundFont 已加载。
  • slot 时钟模型：tempoAnchor + 120 slots/拍，与 Java 对齐。
  • LSTM/RNN、倒影/逆行（MotifTransform）、和声/色彩/节奏模块。

需要新建（按优先级）

  • a. CoreMIDI 输入：MIDIClient + 输入端口 + 解析 MIDIPacketList（note on/off + 力度 + 时间戳）。
  • b. 实时录音器：把 MIDI 包按 slot 量化写入 MelodyPart，做延迟补偿。
  • c. 统一主时钟：驱动伴奏并实时给出 slot 位置（替代 Sequencer）。
  • d. ActiveTrading 状态机：slot 边界在 USER / PROCESS / COMPUTER 间切换。
  • e. 动态实时调度：把“边界处才生成”的回应在 computer turn 精确排入采样器（区别于现在的预渲染）。
  • f. 两个小组件：AbstractMelodyExtractor（约 553 行）、PhraseTable（约 130 行）。

六、移植路径方案

推荐 A. 原生 Swift 重写交互层

保留你已移植的生成引擎，用 CoreMIDI + 自建时钟 + 状态机把“实时输入/轮流”补齐。

  • App Store 质量、最好维护、IP 最干净。
  • 你已经走在这条路上，连续性最好。
  • 工作量集中在基础设施，而非算法。

意义不大 B. j2objc 转换纯逻辑

Google 的 Java→Obj-C 工具（2025 仍维护，需 Xcode 16/JDK21）。

  • 不支持 javax.sound，时钟/发声仍要手写。
  • 且 Java 生成逻辑与 Notate/LickgenFrame 等 GUI 耦合，需先解耦。
  • 你已手工移植生成引擎，收益有限。

可参考 C. C++ 跨平台内核

GimmeDaBlues 即“Max/MSP 原型 → 跨平台 C++ 引擎 + 原生 UI”。

  • 适合未来多端复用（Android/桌面）。
  • “记忆”模式可参考开源因子预言机项目 Djazz。
  • 对当前单端 iOS 略重。

社区调研结论：官方仓库（约 160 stars / 33 forks / 31 issues）中没有任何移动/iOS 移植；同名 App（iMproviser、ImproSnap 等）均与本功能无关。可直接借鉴的是 GimmeDaBlues（iOS 已验证，闭源）与 Djazz（开源，记忆/重组思路），没有现成可抄的 iOS 版 Trading 代码。

七、关键技术难点与风险

1. 时钟与“轮流”的精确性（决定对话感）

电脑回应必须在小节边界准时进入、准时结束，不能抢拍或拖拍。需要音频线程级的时钟与调度，而不是普通 Timer。这是最容易“能跑但不像对话”的地方。

2. 动态（非预渲染）调度

你现在是把整段先排好再播；Trading 的回应在轮到电脑前一刹那才生成，需要“边播边排”的 look-ahead 调度队列。

3. 延迟与补偿

MIDI 输入到音频出声有缓冲延迟，需调小音频缓冲（如 128–256 采样）并像 Java 那样做 offset 校准，否则你的录音会整体偏后。

4. 音频会话 / 后台 / 蓝牙 MIDI

处理中断、耳机拔出、USB 键盘供电、蓝牙 MIDI 抖动；保证屏幕/后台行为符合预期。

八、授权问题（必须先解决）

Impro-Visor 采用 GPL-2.0（GPL v2，或更高版本），是强传染（copyleft）许可证：

  • 若你直接移植/改写其代码（含你已移植的 Transform/Grammar/Style 等），分发的 App 原则上也必须以 GPL 开源、提供完整对应源码。
  • 仓库里的数据文件（.transform、.grammar、风格等）同样在该仓内，不能简单当作“可随意商用的素材”。
  • 你的 RealimPro 目前是闭源 + 内购（含 IAP/Paywall），与 GPL 直接冲突，需要在上线前解决。

三条合规路径：

  • ① 把 App 按 GPL 开源（最简单，但与商业化模式冲突）；
  • ② 联系版权人 Bob Keller / Harvey Mudd College 申请单独的商业授权（作者历来对社区友好，值得发邮件询问）；
  • ③ 干净室重写引擎，并用自己训练/编写的规则与数据（工作量更大，但 IP 最干净）。

建议在投入大量开发前先确认授权，避免后期返工。

九、工作量估算与建议路线（粗略）

分阶段路线

1
M1 输入与时钟：CoreMIDI 输入 + 录音器 + 统一主时钟（能在屏幕上看到自己弹的音符被准确记录）。
2
M2 跑通对话：ActiveTrading 状态机 + 动态调度，先用 Repeat 模式实现“人 4 小节 / 电脑回 4 小节”。
3
M3 接入生成引擎：接上 Transform / Grammar / rectify，实现核心“风格对话”。
4
M4 补全与打磨：Abstract / PhraseTable、延迟校准、谁先开始、轮长设置、手感与 UI。

粗略工作量（1–2 名熟悉音频的开发）

MVP（M1–M2，能 Repeat 对话）约 5–7 周
核心体验（+Transform/Grammar）约 8–10 周
完整 7 模式 + 打磨约 11–14 周

生成算法（最大头、最难的部分）你已完成，因此整体工作量比“从零移植”显著降低；时间主要花在实时基础设施与“手感”调优上。以上为经验估算，实际取决于实时音频经验与 UI 复杂度。

最终结论：Trading 的“实时 MIDI 输入 + 互相用音乐对话”在 iPad 上完全可以实现，且平台非常适合；但不存在“完美 1:1 搬代码”的捷径——javax.sound Sequencer 时钟与发声链路必须用 CoreMIDI + AVAudioEngine 重新设计。你已完成最难的生成算法（Transform/Grammar/Style/LSTM），剩下的核心是实时输入、统一时钟、轮流状态机与动态调度，并务必先处理 GPL-2.0 授权。建议按 Repeat→Transform→Grammar 的顺序先做出可对话的最小闭环验证手感。
